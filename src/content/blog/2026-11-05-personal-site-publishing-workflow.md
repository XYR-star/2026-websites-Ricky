这次整理个人网站，最开始的目标很简单：用自己的域名搭一个可以公开访问的网站，成本尽量低，以后能够持续写文章，也能做一些小功能。

当时我已经把 GitHub、Vercel 和 Cloudflare R2 陆续接上了，但很长一段时间里，我仍然没有完全弄清楚：代码放在哪里？图片为什么还要单独存？在 Vercel 配好 R2 密钥，是不是就代表网页已经会用 R2？如果要发一篇带图片的游记，是不是每次都得回到这台电脑？

真正把链条走通以后，我才发现，需要分清楚的事情其实有两类：**写内容，以及开发网站。**

现在，我可以从浏览器进入后台，保存草稿、上传图片、预览并发布游记；页面布局和交互则继续通过代码仓库维护。这篇文章记录目前这套实际运行的方案，也给未来维护网站的自己留一份说明。

## 一、先把各个服务的职责摆清楚

目前网站使用 Astro 构建页面，配合下面几个服务：

| 环节 | 我用的工具 | 负责什么 |
| --- | --- | --- |
| 页面与样式 | Astro、HTML、CSS、JavaScript | 决定网站长什么样、文章如何展示 |
| 代码与文章版本 | Git、GitHub | 保存源代码、Markdown 文章和修改记录 |
| 网页编辑后台 | Decap CMS | 提供标题、正文、封面、预览和发布界面 |
| 后台登录与仓库连接 | Decap Turbo | 验证编辑者身份，并在服务端访问 GitHub |
| 网站构建与上线 | Vercel | 根据仓库提交构建网站，提供预览和正式部署 |
| 图片与素材 | Cloudflare R2 | 保存上传的图片原文件 |
| 上传与素材列表接口 | Cloudflare Worker | 接收文件、检查请求、读写 R2、返回图片地址 |
| 上传入口的访问控制 | Cloudflare Access | 限制谁可以进入上传器和素材列表 |
| 网站与素材地址 | 自定义域名 | 给读者提供稳定的网站和图片访问地址 |

我现在的网站入口是 [www.heyrickishere.com](https://www.heyrickishere.com/)，内容后台位于 [网站的 `/admin/`](https://www.heyrickishere.com/admin/)，图片使用 `assets.heyrickishere.com` 这个子域名。

网站域名和素材域名属于同一个站点体系，但背后连接的是不同服务：前者由 Vercel 提供页面，后者连接 R2 中的公开素材。

这套方案里，编辑、发布和存储都有服务端参与。我把需要的功能交给现成服务，并用一个 Worker 补齐图片上传这一段，日常维护便围绕这些明确的职责展开。

## 二、一个网站，实际有三条经常使用的路径

### 1. 写文章：浏览器到 GitHub，再到 Vercel

```text
浏览器打开 /admin/
    ↓
Decap CMS 编辑，Turbo 处理登录和 GitHub 请求
    ↓
保存草稿到 GitHub 的文章分支，创建 PR
    ↓
内容检查与预览部署
    ↓
设为“就绪”，点击发布
    ↓
PR 合并到 main
    ↓
Vercel 构建并更新正式网站
```

后台里的文章仍然是仓库中的 Markdown 文件。Decap Turbo 官方文档也说明，保存会产生真实的 Git 提交，Turbo 负责编辑者认证和访问 Git 平台的过程，内容仍留在 Git 中。[参考：Decap Turbo 工作原理](https://decapcms.org/docs/turbo-how-it-works/)

这让图形化编辑和代码维护能够接在同一套版本记录上：我可以在网页中写游记，也可以在本地查看文章文件及其修改历史。

### 2. 上传图片：浏览器到 Worker，再到 R2

```text
在编辑器中选择图片
    ↓
打开受 Cloudflare Access 保护的素材窗口
    ↓
浏览器把图片提交给 Worker
    ↓
Worker 校验请求、格式与大小
    ↓
通过 MEDIA 绑定写入 R2
    ↓
返回 assets 子域名下的图片链接
    ↓
编辑器将链接用于封面或正文
```

这里记录的是当前采用的实现：**文件请求先到 Worker，再由 Worker 写入 R2。**

早期讨论过的“由服务端签发临时上传地址，让浏览器直传 R2”属于另一种设计。本次已经验收的上传器采用上面这条路径，维护时应该以实际运行的代码为准。

图片上传以后，我可以在素材窗口里直接选用。编辑器会接收返回地址，填入封面或正文，省去了手动去存储桶查找文件、复制链接的步骤。

### 3. 读文章：访问网页，再读取公开图片

```text
读者打开文章
    ↓
Vercel 返回构建好的网页
    ↓
浏览器按照网页中的图片链接请求 assets 子域名
    ↓
Cloudflare 提供 R2 图片，并按缓存规则加速
```

普通读者看图时，不需要登录我的上传器。上传管理入口和公开图片地址分别承担管理与展示的职责。

## 三、为什么图片放 R2，文章却留在 GitHub

文字很适合用 Git 管理。文章通常体积不大，前后版本的差异也容易阅读。标题改了什么、正文加了哪一段，都可以留在提交记录里。

照片的情况不同。一篇游记可能有很多张几 MB 的原图。频繁把这些大文件加入代码仓库，会让仓库克隆、同步和后续维护变得笨重。

因此，这次新增的图片主要放入 R2，文章保存图片 URL。仓库中原有的图片路径仍继续兼容，后续再根据需要处理历史素材。

正文中的引用大致是这样：

```markdown
![山间的湖水](https://assets.example.com/cms/travel/文章目录ID/图片ID.jpg "照片说明")
```

这个例子使用示意域名。真正保存到文章里的链接，会由素材窗口自动返回。

由此也能理解，先前在 Vercel 中配置 R2 的访问密钥究竟做了什么：它为读取这些变量的服务端代码提供访问条件。要让某个页面真正展示、上传或管理文件，还需要相应代码调用存储服务。

目前这条编辑器图片链路使用的是 **Worker 的 R2 绑定**。浏览器里的编辑器不需要持有 R2 的长期访问密钥；先前 Vercel 服务端的 R2 配置，则由使用它的其他接口独立维护。

## 四、多设备写作靠的是保存到云端的草稿

一开始，我担心写作后台仍然依赖本地电脑：电脑关机以后，是不是就无法继续编辑？

这次迁到线上后，日常写作可以从能够访问后台、完成登录的设备开始。保存成功的草稿在 GitHub 中，另一台设备登录后台后，可以继续读取。

不过，“编辑框里已经输入”和“云端已经保存”是两个不同状态。我的日常操作会是：

1. 打开文章，填写标题、简介和正文。
2. 上传或选择已有素材。
3. 点击保存，等界面显示“修改已保存”。
4. 换设备继续写之前，确认已经保存最新内容。
5. 预览并检查图文，将状态改为“就绪”后发布。

这次验收专门做了保存后刷新页面的测试，草稿仍然可以重新读取。

目前它适合单人、多设备接续写作。我会先在一个设备保存，再到另一个设备继续。这版没有实现多人协同编辑，也没有采用最早设想的 R2 草稿条件写入机制；两台设备同时修改同一篇文章时，仍需要注意各自打开的版本。

第一版后台目前开放的是**游记**。博客和研究文章的在线编辑配置还可以继续扩展，网站已有的这类内容仍能按原来的仓库流程维护。

## 五、图片如何归类，旧素材又如何复用

### 使用稳定的文章目录 ID

新的游记有一个自动生成的 `media_id`，图片按照文章目录归类，结构类似：

```text
cms/
└── travel/
    └── 文章素材目录ID/
        ├── 图片ID-1.jpg
        └── 图片ID-2.png
```

文章目录和图片对象使用稳定或随机 ID，素材列表同时保留上传时的原文件名作为识别信息。

我最初希望直接按文章标题命名文件夹，后来采用了稳定 ID：文章改标题以后，已有图片目录和链接可以继续使用。目录本身负责稳定引用，原文件名帮助人在素材窗口中找到照片。

这个实现也有边界。复制一篇文章时，需要留意是否同时复制了素材目录 ID，避免把两个文章误当成同一组素材。日常新文章优先使用“新建”。

### 复用已有图片

素材窗口目前有“本篇素材”和“旧素材”两个入口。“本篇素材”读取当前文章目录；“旧素材”兼容同一存储桶早期放在 `cms/` 下、尚未按文章分组的图片。

选择已有图片会复用原文件和链接。这次我们已经验证过，早期上传的图片能够再次用于正文。

现阶段，这个列表还不是整个 R2 账号的全局文件管理器。其他存储桶中的图片，以及其他文章目录中的图片，不会自动全部汇总到这里。以后确实需要跨文章搜索时，再扩展对应的索引和界面。

素材删除也暂时保持谨慎。一个对象可能同时被封面、正文、草稿和其他文章引用，清理之前应先查清引用关系。

### 保留原图，优化加载顺序

我目前更重视照片质量，因此上传保留原文件，不做压缩或转码。现有上传器支持 JPG、PNG、WebP、GIF、AVIF，代码中的大小上限为 `15 × 1024 × 1024` 字节，界面显示为 15 MB。

为了改善阅读体验，我们先调整了加载方式：封面优先加载，正文图片在生成页面时带上延迟加载与异步解码设置；素材列表中的原图按需打开预览。

保留原图意味着首次下载仍需要传输完整文件。缓存和延迟加载能改善访问过程，但不会把几 MB 的照片变成小文件。未来如果需要缩略图，可以保留原图，再单独生成展示版本。

## 六、为什么从 r2.dev 换成素材子域名

开发阶段，`r2.dev` 地址很方便，可以先确认文件已经上传、链接能够访问。准备正式展示时，我给素材桶绑定了 `assets.heyrickishere.com`。

Cloudflare 将 `r2.dev` 定位为非生产用途的开发访问方式，并说明自定义域可以使用 Cloudflare 缓存等能力。[参考：R2 公开存储桶与自定义域](https://developers.cloudflare.com/r2/buckets/public-buckets/)

实际切换分成了几步：

1. 在 R2 的素材桶中添加自定义域名，等待连接有效。
2. 用已有图片确认 HTTPS 链接可以读取。
3. 给上传 Worker 设置 `MEDIA_PUBLIC_BASE`，让它返回新域名的链接。
4. 核对编辑器允许接收的图片来源。
5. 更新测试文章中已经保存的旧链接，并验证展示和缓存。

这里有个很容易忽略的细节：修改上传器的返回地址，会影响之后上传、选用素材时返回的链接，已经写进 Markdown 的旧 URL 还需要另外处理。切换期间，要先照顾好这些已有引用。

这一步让“网站地址”和“素材地址”更清楚，也给后续更换底层实现留下了空间。

## 七、预览、发布与上线，分别代表什么

这次最容易混淆的，就是看到了某个成功提示以后，以为所有环节都已经完成。

| 当前看到的状态 | 实际说明 |
| --- | --- |
| 图片上传成功 | 文件已经保存到 R2，并取得了可用地址 |
| 编辑器预览正常 | 当前编辑内容能够在后台渲染 |
| 修改已保存 | 文章修改已经写入云端草稿 |
| Vercel 预览部署成功 | 对应分支能够构建出可访问的预览版本 |
| 后台显示“已发布” | 本次文章修改已经合并到正式目标分支 |
| Vercel 正式部署成功 | 对应提交已经部署到正式网站 |

我们先在 `decap-preview` 分支试用，验证编辑器、保存、图片和发布。这期间，点发布更新的是预览分支。

转正式时，才把后台的发布目标切换为 `main`，并同步修改 Turbo 中的后台地址、配置路径，以及 Worker 允许返回的正式编辑器地址。旧试用入口随后跳转到正式后台。

Vercel 的 Git 集成会根据配置的生产分支创建正式部署，其他分支通常用于预览。因此，仓库中的发布目标和 Vercel 的生产分支必须对应起来。[参考：Vercel 的 Git 部署机制](https://vercel.com/docs/git)

后台显示“已发布”后，我仍会等待对应提交的正式部署完成，再打开公开页面确认。如果新版本构建失败，上一版成功部署的网站通常仍在服务，而文章提交也仍有记录，可以继续修正。

## 八、安全要落实在具体入口和发布规则上

这次没有把“后台页面不放在导航里”当成访问控制。几个关键入口分别处理：

**后台登录。** 编辑器通过 Turbo 登录，站点成员权限决定谁可以访问相应内容。个人电脑用 SSH 推送 GitHub，则是另一条认证路径；SSH 连通，不代表网页后台自动获得了权限。

**图片管理。** 上传器和素材列表由 Cloudflare Access 保护。Worker 检查授权上下文，上传请求还要通过来源、格式、文件内容和大小检查。

**图片回传。** 素材窗口只向预先允许的编辑器地址回传结果。编辑器也会核对来源窗口、来源域、请求标识和图片地址，避免错误窗口把图片填到另一篇文章里。

**正式发布。** GitHub 的 `main` 启用分支保护，要求通过 PR 和 `CMS content changes` 检查，并将检查来源限定为 GitHub Actions。发布应用没有获得绕过这些要求的权限。

目前的内容检查会限制 CMS 草稿 PR 只改对应游记及兼容的旧素材文件，阻止夹带网站配置、删除操作或符号链接等改动。它约束的是 CMS 发布范围；普通代码开发 PR 仍可以修改布局和程序。

单人使用时，我保留了 PR 与检查流程，同时关闭“必须有人批准”的人数要求。这样能够自己完成发布，也让服务端规则负责拦截越过正常发布流程的写入。GitHub 公开仓库可使用相应分支保护能力。[参考：GitHub 分支保护规则](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)

还有一个发布前必须理解的边界：**当前 GitHub 仓库是公开的，草稿分支中的文字也可能被读取；图片上传到公开素材桶后，也已经具有公开链接。** 后台登录和上传器保护，并不等于这些内容适合存放私人资料。

原图还可能包含拍摄位置等元数据。准备公开照片时，这也是内容整理的一部分。

## 九、以后改布局，还要修改 Worker 吗

日常改网站，我会先判断改的是哪一部分。

| 想做的修改 | 通常需要改哪里 |
| --- | --- |
| 首页布局、文章排版、导航、字体、颜色、响应式样式 | 网站仓库中的页面、组件和样式，由 Vercel 部署 |
| 新增公开页面或前端交互 | 网站仓库中的相应代码 |
| 后台字段、文章预览模板、编辑器界面 | 仓库中的 Decap 配置与前端代码 |
| 增加博客或研究文章的后台管理 | CMS 集合配置、内容结构、预览及发布检查；按需求复用现有上传能力 |
| 上传素材弹窗的布局、列表逻辑、文件校验 | Worker 源码；这张弹窗页面本身由 Worker 提供 |
| 调整格式、大小限制、目录规则或回传协议 | 核对并修改 Worker 与编辑器相关代码 |
| 更换编辑器域名、素材域名或访问控制 | 核对平台设置、Worker 配置和前端来源限制 |

因此，普通的页面排版修改，沿着 GitHub 到 Vercel 的工作流走就可以。

但我也要记住：**Worker 是另一份独立部署的程序。** 它的源码虽然保存在同一个仓库里，当前仍由 Cloudflare 单独部署。把修改提交到 GitHub，不会自动更新正在运行的 Worker。以后真正修改这一部分时，需要同时完成源码记录和 Cloudflare 部署。

### 代码开发的日常步骤

整理好当前工作区后，可以从最新的主分支建立功能分支：

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/article-layout
```

修改页面与样式，检查构建结果，再提交具体文件：

```bash
npm run check
npm run build

git add src/layouts/PostLayout.astro src/styles/global.css
git commit -m "Adjust article layout"
git push -u origin feat/article-layout
```

接着在 GitHub 创建 PR，查看差异和 Vercel 预览，确认后合入 `main`，等待正式部署。

由于主分支保护已经启用，日常流程也从“直接推送主分支”变成了“功能分支、PR、合并、部署”。即使是一个人的网站，这样也方便在正式展示前检查修改。

## 十、这次真正踩过的几个坑

### 1. 配好了服务，不等于功能已经实现

最初我反复确认 Vercel 和 R2 有没有“接上”。后来才把判断方式换成实际操作：能否上传、能否返回链接、能否保存引用、能否在正式文章中显示。

账号授权、环境变量、存储桶绑定，解决的是访问条件；一次完整的图文发布，才能验证这些条件是否被代码正确使用。

### 2. 后台登录成功，也可能回不到新域名

从预览域名切到正式域名时，Turbo 里实际保存的后台地址仍是旧值。结果是账号已经登录，跳回正式编辑器时却被拒绝。

修正站点的 Admin interface URLs、分支和配置路径以后，正式后台才顺利打开。迁移时应该核对平台上已经保存的值，而不只看本地代码。

### 3. 一个多余字符就能让素材窗口不可用

素材域名变量末尾曾多出一个反引号。页面看上去很接近正确地址，Worker 却会将它判断为无效 URL。

最后把变量值重新填写为完整、纯净的 HTTPS 地址并部署，素材列表与选图回传就恢复了。复制配置时，要区分变量名称、实际值和 Markdown 的格式符号。

### 4. 图片已上传，但后台预览仍可能出错

存储桶里有文件，还要继续检查文章引用的 URL、相对路径解析和编辑器预览方式。素材窗口能够显示照片，也不能代替封面预览、正文预览和正式页面的分别验证。

### 5. 试用后台和正式后台不能长期混用

当前草稿分支按文章类型和文件名生成，同一篇文章的试用与正式草稿可能使用相同分支名。正式切换以后，我统一使用正式后台，旧入口跳转过去，减少误写目标分支和混用旧草稿的机会。

## 十一、这次如何确认链条真的走通

最后的验收使用了一篇现有测试游记。我们实际完成了下面这些操作：

1. 在正式域名登录后台，读取文章列表和正文。
2. 打开 R2 素材窗口，选用已经上传的照片，确认能回传到正式编辑器。
3. 对测试文章做轻微格式更新，保存后刷新，确认云端草稿仍在。
4. 核对草稿 PR 的目标是 `main`，且差异只有对应文章。
5. 等待内容检查和 Vercel 预览部署通过。
6. 将草稿设为“就绪”，从后台完成发布。
7. 确认 PR 已合并，主分支保护仍然启用。
8. 按合并提交核对 Vercel 正式部署成功，再读取公开文章、封面和正文图片。

这比单独看到“上传成功”“修改已保存”或“已发布”更有意义：编辑器中的一次操作，最终确实变成了公开网站上的一个版本。

接下来，我可以把更多时间放回文章和页面本身。写游记时打开后台，改排版时打开代码仓库；GitHub 留下修改记录，Vercel负责把通过确认的版本上线，R2 继续保存照片。以后需要扩展功能，也可以沿着这些职责逐段调整。
